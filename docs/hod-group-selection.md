# Выбор групп заведующим кафедрой

Страница: `/csh/hod/groups`. Оформление и область истории переиспользуются со страницы ЛПР `/csh/lpr/list2`.

## Работа страницы

- Заведующий видит только профили своей кафедры. Фильтры факультета и направления, сортировка, строки направлений, объединённые ячейки профилей и история восьми семестров переиспользуют оформление страницы ЛПР. В окне истории одновременно видны три семестра.
- В каждой ячейке текущего семестра один чекбокс из общего компонента `CheckBox`, размером 18×18. Изначально отмечен выбор ЛПР, после подтверждения отображается сохранённое решение кафедры.
- «Подтвердить и сохранить» сохраняет изменённые решения и неподтверждённые рекомендации видимых профилей. Изменения, сделанные до смены фильтра, также сохраняются. Для профиля без рекомендации группа выбирается явно.
- Ручную рекомендацию ЛПР можно снять и заменить другой допустимой активной группой того же `StudyProgramId`. Пока группа отмечена, остальные чекбоксы профиля заблокированы. Автоматическое назначение можно отменить или восстановить исходную группу. Другие группы заблокированы также на бэке, в том числе после сохранения отмены и повторного открытия страницы.
- Нажатие на ячейку вне чекбокса открывает модалку причины. Снятие отметки также открывает эту модалку. Изменение применяется к локальному выбору после «Применить», закрытие или «Отмена» сохраняет прежний выбор. Для отклонения от рекомендации обязательна причина до 1000 символов. Запись в БД выполняется общей кнопкой сохранения таблицы.
- Одновременно участвует не более одной группы профиля в семестре. Сохраняются правила цикла и запрет повторения группы в соседних семестрах; для единственной активной группы действует прежнее исключение — она может участвовать каждый семестр. Архивные группы не предлагаются для новых назначений.
- Будущие рекомендации доступны для просмотра. Текущая замена учитывается при расчёте будущих автоматических назначений. Если она конфликтует с будущим ручным назначением ЛПР, пакет отклоняется: ручные решения не стираются автоматически.
- Решения ЛПР и HOD хранятся отдельно. На странице ЛПР отображаются исходная рекомендация и отметка «Кафедра: участвует / не участвует», причина доступна при наведении.

## Последующие этапы

Подтверждение участия открывает группу на странице выбора дисциплин и создаёт два пустых `Testing` со ссылкой на решение кафедры. При сохранении дисциплин эти записи связываются с отчётами. При замене группы до назначения дисциплин прежние пустые записи удаляются.

Когда по профилю уже назначены дисциплины, преподаватели, параметры проведения или есть отчёт, сменить группу нельзя. Сохранение выбора групп и запись дисциплин используют одну блокировку плана и обновляют его версию.

`GroupDiscipline/GetGroups` использует итоговый выбор HOD и текущий календарный семестр. Ранее он выбирал самый поздний семестр справочника. Старые процессы с уже выбранными дисциплинами продолжают отображаться и без новой записи решения.

## API

- `GET /csh/api/HodGroups/GetGroups` — кафедра, таблица плана, рекомендации и допустимые решения. Кафедра берётся из `ICurrentUserProvider`, клиент её не задаёт. Если ЛПР ещё не сформировал план текущего периода, возвращается `plan: null`.
- `PATCH /csh/api/HodGroups/UpdateGroups` — атомарное сохранение пакета:

```json
{
  "currentSemesterId": 17,
  "version": 4,
  "decisions": [
    { "studyProgramId": 10, "selectedGroupId": 42, "reason": "Замена рекомендованной группы" },
    { "studyProgramId": 11, "selectedGroupId": null, "reason": "Нет возможности провести проверку" }
  ]
}
```

Числа в примере условные: клиент передаёт реальные ID из ответа. `selectedGroupId: null` означает отказ от участия профиля в этом семестре. HTTP 403 — чужая кафедра, 400 — некорректный запрос/нет причины, 409 — изменившаяся версия, нарушение цикла или уже начатая работа. Никакая часть невалидного пакета не сохраняется.

## Изменения БД

Миграция `20261108233329_AddHodGroupParticipation` добавляет:

- `study_groups.is_active`, по умолчанию `true` для существующих и новых групп;
- `group_participation_decisions`: профиль, семестр, исходная рекомендованная группа, итоговая группа, причина, автор и дата. Пара профиль–семестр уникальна;
- `testing.group_participation_decision_id` — связь фактического тестирования с решением кафедры.

`recommendation_history` продолжает хранить рекомендации ЛПР. Подмена групп не создаёт фиктивную рекомендацию взамен исходной. Если исходную группу архивировали после рекомендации, текущая рекомендация остаётся видна, чтобы заведующий мог зафиксировать причину и замену.

Архивирование представлено полем модели; отдельная кнопка архивирования на странице HOD не добавлялась. История групп сохраняется. Для работы необходима новая миграция; создание миграции не применяет её к рабочей БД. При пересборке и запуске API проект применяет миграции автоматически.

При входе через ЕУЗ API проверяет сессию и берёт пользователя и кафедру из `users`. При `MOCK_AUTH_ENABLED=true` в локальном тестовом режиме используются `TEST_USER_ID` и `TEST_DEPARTMENT_ID`.

## Основные файлы

- Бэк: `GroupsTestingService.cs`, `GroupsTestingService.Participation.cs`, `HodGroupsController.cs`, `GroupDisciplineService.cs`, `GroupDisciplineRepository.cs`.
- Фронт: `frontend/app/hod/groups/page.tsx`, `frontend/services/hodGroups.ts`, общие стили и история из `/lpr/list2`.
- Регрессионные проверки: `KnowledgeApp.Planning.Tests/HodParticipationChecks.cs`. Флаг `--hod-integration` с `LPR_REPORT_TEST_SERVER` проверяет полный процесс и миграции на отдельной временной MySQL-базе `hod_groups_check_<guid>`, удаляемой после проверки. Рабочая БД не используется.
